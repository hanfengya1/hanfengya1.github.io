Skill

  2. 写好 SKILL 的核心是痛点驱动、抽离优先、范例比规则管用。

langchain

LangChain将开发者的工作重心从「适配底层接口」转移到「设计AI业务功能」。

  • 原生LLM开发存在的实际难题
    单一功能开发难度不高，但多需求叠加后，开发者80%工作量都在重复封装底层逻辑，无法聚焦业务功
    能本身。

  • LangChain 不便的地方*(基本面试必问)

  1. 依赖过多，复杂度高
    LangChain集成了大量向量数据库，模型提供商和工具，虽然理论是可选，但是实际使用中很多功
    能需要安装一堆依赖，导致项目臃肿，容易出现”依赖地狱”，对于只需要简单功能的项目，这种设计显
    得过度。
  2. 频繁更新，接口不稳定
    LangChain迭代速度太快，但是带来大量破坏性更新，API接口经常变化，文档之后，导致开发需要
    不断重构代码，维护成本高。
  3. 性能和延迟问题
    LangChain的链式调用每一步都可能涉及外部API，导致延迟明显，尤其是需要实时响应的场景中表
    现不佳，链式调用其实也增加了出错概率和调试难度。
  4. 不够灵活，定制困难
    高度抽象导致很多底层逻辑无法轻易改变，遇到特殊需求时，开发者往往需要绕过框架，甚至重写
    部分功能。

  • LangChain 存在诸多缺点，为什么还是主流？
    面试答案：LangChain的短板是框架封装带来的工程代价，但它统一了大模型应用开发标准，封装
    了文档处理、向量检索、多模型适配、Agent工具链等海量通用逻辑，能让开发者不用重复造轮子，快速
    落地复杂LLM业务。同时版本锁定、链路缓存、自定义Runnable等方案可以规避它大部分缺陷，因此工
    业界依然广泛使用。

  • 什么时候不用 LangChain（边界区分，面试加分）

  1. 超轻量需求：仅单次简单翻译、单轮问答，无知识库、无工具调用；
  2. 极致低延迟服务：毫秒级响应刚需，无法承受链式封装损耗；
  3. 全部底层高度自定义：整套模型、检索、流程逻辑都需要完全自研。
  • 面试题

项目开发环境搭建

uv：新一代轻量化工具，Rust底层开发，速度比pip快数十倍，自动创建虚拟环境、锁定依赖版本。
执行后目录新增文件：

  • .venv/ ：独立虚拟环境，所有依赖安装在此，不会污染全局Python
  • pyproject.toml ：记录我们手动需要安装的依赖包
  • uv.lock ：自动生成锁文件，锁定所有包精确版本，保证环境可复现

三种消息传⼊⽅式

  1. 直接传⼊字符串（单轮简单问答）
    局限：⽆法设置⻆⾊、⽆历史对话。⽆法设置系统⻆⾊（没有SystemMessage），⽆法多轮对话（没有
    AIMessage历史）
    适⽤场景：快速测试，临时脚本，最简单的问答。
  2. 传入消息列表（课程最常⽤，多轮/⻆⾊设定）
  3. 元组/字典动态构造（接⼝/配置读取场景）
    局限：无法识别数据类型
    适⽤场景：从数据库读取字典、元组的数据，从前端读取json数据。

如何决策⽤哪个：

  • 只是⼀个临时测试？→ ⽤字符串
  • 代码要上⽣产？→ ⽤消息列表
  • 数据来⾃数据库/API？→ ⽤字典

、四⼤标准调⽤⽅式（同步/异步/流式/批量）

  • 同步（串⾏）（invoke）：总耗时 = 所有请求时间之和
  • 异步（并⾏）（ainvoke）：总耗时 ≈ 最慢⼀条请求的时间
  • 流式 打字机实时输出 聊天界⾯必备，逐Token打印，提升交互体验
  • 批量（批量）：批量处理多条消息，提高效率，但需要处理并发问题。

⾯试题：⼗⼤⾯试⾼频题 + 标准话术

Q1：什么是Model I/O？

Model I/O是LangChain最核⼼的模块，标准化了’输⼊提示→模型推理→结果解析’全流程。分为Prompts（加⼯输⼊）、Models（模型调⽤）、Output Parsers（输出解析）三个⼦模块。⼀句话：它是所有⼤模型交互的统⼀⼊⼝和出⼝。

Q2：ChatModels和LLMs的区别？

“ChatModels接收消息列表（每条消息带role），理解对话上下⽂，是当前主流。LLMs接收纯字符串做⽂本补全，⽆对话概念，已被淘汰。我的项⽬全程使⽤ChatModels，因为System Prompt⻆⾊控制和多轮对话是刚需。

Q3：原⽣requests vs LangChain的核⼼差距？

⼋个维度中最重要的三个：第⼀，换模型——原⽣要改请求头、请求体、返回值解析三层代码，LangChain只改⼀⾏初始化。第⼆，消息管理——原⽣⼿动拼role/content字典易出错，LangChain⽤SystemMessage/HumanMessage/AIMessage对象有类型检查。第三，调⽤⽅式——原⽣每个⼚商流式/异步写法不同，LangChain统⼀invoke/stream/batch/ainvoke。

Q4：temperature怎么选？举三个具体例⼦。

代码⽣成/翻译⽤00.3（每次输出必须⼀致），知识问答⽤0.30.7（准确但表达可灵活），⽂案创意⽤0.7~1.0（多样性）。核⼼原则：确定性任务低temperature，创意性任务⾼temperature。

Q5：消息传⼊有哪三种⽅式？

字符串（ invoke('你好') ，单轮快速测试），消息列表（ invoke([SystemMessage(...), HumanMessage(...)]) ，⽣产标准写法），字典列表（ invoke([{'role':'user','content':'...'}]) ，数据库/API读取场景）。⽣产推荐⽤消息列表——IDE有⾃动补全和类型检查。

Q6：invoke/ainvoke/stream/batch怎么选？

invoke⽤于同步单次请求，ainvoke⽤于异步Web服务⾼并发，stream⽤于聊天界⾯逐字打印，batch⽤于批量独⽴问题的并发处理。关键区别：串⾏(invoke)总耗时=所有请求之和，并⾏(ainvoke/batch)总耗时≈最慢⼀条的时间。

Q7：怎么在LangChain中对接Ollama本地模型？

“⽤ChatOllama类，model填本地的模型名（如qwen3.5:4b），base_url填localhost:11434。和云端DeepSeek的区别仅在于初始化代码不同——后续invoke/stream/batch调⽤语法完全⼀样。这意味着我可以先在线开发测试，然后零成本迁移到本地部署。

Q8：怎么统计多次调⽤的累计Token消耗？

⽤get_usage_metadata上下⽂管理器——with包裹多次invoke调⽤，退出后通过cb.usage_metadata获取聚合的input_tokens/output_tokens/total_tokens。适合按⽤户会话做成本核算。

Q9：你⽤什么类调DeepSeek？为什么？

“⽤ChatOpenAI。因为DeepSeek的API完全兼容OpenAI格式——包括请求体结构、鉴权⽅式、返回值格式。所以⽤ChatOpenAI配合DeepSeek的base_url就能调⽤。不是所有的国产模型都⽤专属类——取决于它是否兼容OpenAI格式。

Q10：从DeepSeek切换到通义千问需要改⼏⾏代码？

如果通义千问⽤阿⾥云百炼的兼容模式端点——两个模型都⽤ChatOpenAI类（都兼容OpenAI格式），只需要改3⾏：model从deepseek-v3换成qwen-plus，api_key换百炼的Key，base_url换成百炼地址。invoke/stream/batch业务代码⼀⾏不动。如果⽤通义千问的原⽣DashScope接⼝——导⼊换成ChatDashScope，类名换成ChatDashScope，其他调⽤代码不变。⽆论哪种⽅案，核⼼业务逻辑零改动。
